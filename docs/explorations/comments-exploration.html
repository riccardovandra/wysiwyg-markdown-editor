Comments in the WYSIWYG editor

Select any run of text in this document. A Comment button appears above the selection; the note you type shows up in the left margin, anchored to the line it belongs to. Highlights stay in the text, so the comment survives scrolling, editing around it, and reopening the file.

Why margin bubbles

Inline notes compete with the prose, and a side panel loses the connection to the line. The left margin keeps both: the highlight marks what, the bubble says why, and a leader line ties them together. Reviewers used to Google Docs will not need instructions.

The file on disk stays plain markdown. Each comment is written as {==highlighted text==}{>>note<<}, the CriticMarkup convention, so a teammate reading the raw .md on GitHub still sees the note next to the passage it refers to.

Behaviour to confirm

  • Resolving a comment removes it from the file; the text stays untouched.
  • Deleting a comment removes the highlight and the note.
  • A comment can span inline code, bold text, or several sentences.
  • Bubbles never overlap: when two comments sit on the same line, the second one is pushed down.

The document is editable, like the real editor. Hover a bubble to see its highlight; click a highlight to jump to its bubble.

What gets saved to the file


    

      

        
CriticMarkup Recommended

        
{==text==}{>>note<<}. Plain text, readable in any diff, already understood by iA Writer, Marked 2 and Pandoc filters. GitHub shows the braces literally, which is noisy but keeps the note next to the passage. Resolving a comment strips both parts from the file.

      

      

        
HTML <mark>

        
<mark data-comment="note">text</mark>. Renders as a real highlight on GitHub, but the note hides in an attribute nobody reads, and both marked and turndown need HTML passthrough rules. Better only if GitHub rendering matters more than the note itself.

      

    

  


  

    
How this maps onto the extension

    
    
      
  1. A TipTap Mark named comment with an id attribute, rendered as <mark data-comment-id>. The toolbar-free flow above is editor.commands.setMark('comment', { id }) on the current selection.

  2. Comment bodies live outside the document: a map id → { text, author, createdAt, resolved } in React state. The gutter component positions each bubble with editor.view.coordsAtPos(from) after every transaction and on resize, then pushes overlapping bubbles down, exactly as this page does.
    3. 
      
  3. Save: a turndown rule for mark[data-comment-id] emits {==…==}{>>…<<}. Load: a regex pre-pass in markdownParser.ts turns CriticMarkup back into <mark> before marked runs, so the round trip is lossless.
    4. 
      
  4. Resolve removes the mark and the note from the file. CriticMarkup has no resolved state; if history matters, resolved notes could be kept in frontmatter. That is the one design decision left open.
